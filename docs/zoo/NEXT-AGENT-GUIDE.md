## 3. The acceptance standard

The user's principle is that every numerical function should have defensible
equivalence evidence against an independent source. Apply it to a **specific
definition, parameter setting and graph domain**, not just a measure name.

1. **Pin the definition.** Record the paper/version, DOI or stable URL, equation,
   algorithm and relevant pages. State which source was actually read.
2. **Resolve conventions.** Specify graph direction, weights, loops, parallel
   edges, distance orientation, normalization, parameters and undefined cases.
3. **Calculate an independent reference.** Prefer independent algorithms, exact
   small cases, maintained external implementations and published examples.
4. **Test the public function.** Passing an internal kernel alone is insufficient.
5. **Record limitations and failures.** An unresolved disagreement must remain
   visible. It cannot be removed by retuning defaults or silently widening tolerance.

Keep these evidence categories separate:

| Evidence | What it supports | What it does not establish |
|---|---|---|
| Independently coded equation/oracle | Numerical agreement with the stated definition on tested inputs | Original author software parity |
| Exact enumeration, symbolic or high-precision calculation | Independent small-case or numerical-stability checks | Exhaustive correctness on every graph size |
| Published numerical example | Agreement with that example and its precision | Agreement with every published result |
| Pinned author/external implementation | Agreement with that software within the tested domain | Agreement outside its conventions/domain |
| Rank correlation | Similar ordering of nodes on a benchmark | Equal scores, equal definitions or scientific interchangeability |
| API and package checks | Integration and software behavior | Independent mathematical verification |

Do not describe all 191 runtime measures as newly Nestimate-verified. The ledger's
63 covered original labels have their own explicit scopes and evidence. Likewise,
passing the correlation validator verifies the correlations, not all centralities.

## 4. How definitions and references were obtained

Use the Zoo entry and the candidate CSV as discovery aids. Follow their citations
to the original publisher paper, author preprint, institutional repository or
author code. Read complete equations and algorithm context; inspect PDF pages
visually where text extraction can lose subscripts, signs, summation limits,
figures or table alignment. Metadata and abstracts are leads, not formula evidence.

If the original full text is inaccessible, an explicit reproduction in another
research paper can support a narrowly stated implementation. Record both the
original attribution and the reproduction actually inspected. Do not claim to
have read the original or verified its software. This distinction applies, for
example, to the mixed-gravity implementations in batch 39.

For a useful source, preserve a source audit with:

- Stable URL/DOI, title/year/version, accessed material, equations and page numbers.
- PDF hash or author-code commit and version; locally retained locations.
- Exact formula and conventions; disagreements between prose, pseudocode, tables
  and Zoo summaries, with the chosen interpretation explained.
- Whether numeric reference values were printed in the paper or newly calculated
  from a graph shown in it. Newly calculated values are not published numbers.
- Code/data availability findings. A dataset repository is not author-code evidence.

If evidence is insufficient, retain a pending candidate and a concrete research
lead in `candidate_reviewNN/SOURCE_AUDIT.md`. Do not infer a formula or equivalence
from a large Zoo correlation. Do not contact authors or send messages without
explicit user authorization.

## 5. Implementation and independent verification method

When implementation resumes under user direction, first write down the mathematical
contract. Decide explicitly whether a method retains directed arcs or uses a
simple undirected skeleton; whether reciprocal weights sum; whether loops count;
and whether multiedges carry multiplicity. Pin open versus closed neighborhoods,
ordered versus unordered node pairs, endpoint inclusion, original versus updated
degrees, radius centering, and reachable-node versus whole-graph denominators.

Pin the parameter domain, default and interpretation separately from Zoo's
unknown experimental settings. Test raw scores before normalization. State the
normalization rule and behavior with negative scores, isolates, empty graphs,
singletons, disconnected components, zero spectral radius and overflow.

Choose reference algorithms that can fail differently from production code:

| Method family | Independent checks used in this work |
|---|---|
| Paths and betweenness | NetworkX all-shortest-path enumeration, exact integer adjacency powers, explicit path counts and Fraction arithmetic |
| Cores, trusses and cliques | NetworkX core/truss/clique algorithms, exhaustive induced-subset enumeration and small exact combinatorics |
| Gravity and neighborhood sums | Independently calculated degrees/cores and BFS distances; direct versus nested sums; exact rational small cases |
| Spectral measures | NumPy/SciPy eigensystems, shifted power iteration, SymPy characteristic-polynomial root intervals and mpmath projectors/resolvents |
| Markov and random-walk measures | NetworkX PageRank/line graphs, transition-matrix solutions, Markov-chain tree cofactors and explicit first-visit/walk enumeration |
| Resistance/Laplacian methods | Resistance distances, spanning-tree enumeration, grounded minors, Cholesky/inverse/determinant calculations and high precision |
| Entropy and expected force | Explicit infection-event enumeration, exact boundary-edge counts, direct entropy and high-precision near-uniform cases |

A different language alone does not make an oracle independent. Record shared
primitives and supplement them with a structurally different calculation where
possible. Use author implementations unchanged when claiming author parity; pin
their commit, inputs, supported domain and tolerances.

The later batches reuse a retained collection of **5,532 graphs**: all labeled
simple undirected graphs through five vertices, directed graphs through four,
plus six canonical and 260 seeded random fixtures through 50 vertices. Earlier
batches use other collections; read their manifests rather than assuming this
count applies to them. These are cograph verification fixtures, not Zoo's ICON data.

Parameter sweeps include boundary values, ordinary values, fractional radii,
unlimited radii and explicit exceptional domains where relevant. Separate stress
audits exercise high dynamic range, near singularity, periodic chains, tied
eigenspaces, large integer counts and near-uniform entropy. Use exact/high-precision
references to decide whether production or the floating-point reference failed.

For batch 39, scaled error is `abs(got - reference) / max(1, abs(reference))`
per value, with tolerance `1e-11`. Other batches have their own recorded criteria.
Check vector lengths, node order, finite/undefined classifications and expected
errors as well as numeric tolerances. Never present an undefined result as zero
just to make a comparison pass.

Retain the runner, reference, fixtures, seed/permutations, versions, per-configuration
errors and pass flags. Report comparison counts and scalar-value counts separately.
Do not total overlapping audits into a claim about independent samples.
